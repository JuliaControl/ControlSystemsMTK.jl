ControlSystemsMTK.MultirateLinearization — Type
MultirateLinearization

A linear periodic model of a hybrid system with several clocks, created by multirate_linearization.

The model is defined on the event grid: the sorted set of all instants within one common period Tc at which a clock ticks or a signal of the continuous-time partition is updated or observed. Event k maps the state before the event to the state before the next event,

\[\begin{aligned} x_{k+1} &= A_k x_k + B_k u \\ y_k &= C_k x_k + D_k u \end{aligned}\]

where u contains the lifted inputs of the whole period and y_k the outputs that are observed at event k. The state consists of the state of the continuous-time partition, the state variables of the clocked partitions, one hold variable per clocked signal that is read by another partition, and one hold variable per input of the continuous-time partition. Each partition is represented by one set of Jacobians, evaluated at the operating point and the time of the linearization; a model that depends explicitly on time is not represented.

Fields

  • A, B, C, D: The matrices of each event.
  • output_channels: The lifted output channels observed at each event.
  • Tc: The common period.
  • t0: The instant at which the period starts.
  • event_times: The instants of the events, in [t0, t0 + Tc).
  • x: The names of the state variables.
  • inputs, outputs: The signals, see MultiratePort.
  • hl: The ModelingToolkit.HybridLinearization the model was created from.

See lifted_ss, multipliers, fundamental_response, harmonic_response, performance_frequency_gain, robust_frequency_gain and multirate_margins.

ControlSystemsMTK.GainScheduledStateSpace — Method
GainScheduledStateSpace(systems, vt; interpolator, x = zeros((systems[1]).nx), name, u0 = zeros((systems[1]).nu), y0 = zeros((systems[1]).ny))

A linear parameter-varying (LPV) version of Blocks.StateSpace, implementing the following equations:

\[\begin{aligned} \dot{x} &= A(v) x + B(v) u \\ y &= C(v) x + D(v) u \end{aligned}\]

where v is a scalar scheduling variable.

See example usage in the gain-scheduling example.

Arguments:

  • systems: A vector of ControlSystemsBase.StateSpace objects
  • vt: A vector of breakpoint values for the scheduling variable v, this has the same length as systems.
  • interpolator: A constructor i = interpolator(values, breakpoints) and returns an interpolator object that can be called like i(v) to get the interpolated value at v. LinearInterpolation from DataInterpolations.jl is a good choice, but a lookup table can also be used.

Connectors

  • input of type RealInput connects to $u$.
  • output of type RealOutput connects to $y$.
  • scheduling_input of type RealInput connects to $v$.

ControlSystemsMTK.batch_ss — Method
batch_ss(sys, inputs, outputs, ops::AbstractVector{<:AbstractDict};
            t = 0.0,
            allow_input_derivatives = false,
            kwargs...)

Linearize sys in multiple operating points ops::Vector{Dict}. Returns a vector of StateSpace objects and the simplified system.

Example:

using ControlSystemsMTK, ModelingToolkit, RobustAndOptimalControl
using ModelingToolkit: getdefault
unsafe_comparisons(true)

# Create a model
@parameters t k=10 k3=2 c=1
@variables x(t)=0 [bounds = (-2, 2)]
@variables v(t)=0
@variables u(t)=0
@variables y(t)

D = Differential(t)

eqs = [D(x) ~ v
       D(v) ~ -k * x - k3 * x^3 - c * v + 10u
       y ~ x]


@named duffing = System(eqs, t)

bounds = getbounds(duffing, unknowns(duffing))
sample_within_bounds((l, u)) = (u - l) * rand() + l
# Create a vector of operating points
N = 10
ops = map(1:N) do i
    op = Dict(x => sample_within_bounds(bounds[x]) for x in keys(bounds) if isfinite(bounds[x][1]))
end

Ps, ssys = batch_ss(duffing, [u], [y], ops)
w = exp10.(LinRange(-2, 2, 200))
bodeplot(Ps, w)
P = RobustAndOptimalControl.ss2particles(Ps) # convert to a single StateSpace system with `Particles` as coefficients.
bodeplot(P, w) # Should look similar to the one above

Let's also do some tuning for the linearized models above

function batch_tune(f, Ps)
    f.(Ps)
end

Cs = batch_tune(Ps) do P
    # C, kp, ki, fig, CF = loopshapingPI(P, 6; phasemargin=45)
    C, kp, ki, kd, fig, CF = loopshapingPID(P, 6; Mt=1.3, Tf = 1/100)
    ss(CF)
end

P = RobustAndOptimalControl.ss2particles(Ps)
C = RobustAndOptimalControl.ss2particles(Cs)

nyquistplot(P * C,
            w,
            ylims = (-10, 3),
            xlims = (-5, 10),
            points = true,
            Ms_circles = [1.5, 2],
            Mt_circles = [1.5, 2])

# Fit circles that encircle the Nyquist curve for each frequency
centers, radii = fit_complex_perturbations(P * C, w; relative = false, nominal = :center)
nyquistcircles!(w, centers, radii, ylims = (-4, 1), xlims = (-3, 4))

See also trajectory_ss.

ControlSystemsMTK.build_quadratic_cost_matrix — Method
build_quadratic_cost_matrix(sys::System, inputs::Vector, costs::Vector{Pair}; kwargs...)

Assemble a quadratic cost matrix (for LQR or Kalman filtering) that penalizes states or outputs of system sys according to the vector of pairs costs.

The motivation for this function is that ModelingToolkit does not guarantee

  • Which states are selected as states after simplification.
  • The order of the states.

The second problem above, the ordering of the states, can be worked around using reorder_unknowns, but the first problem cannot be solved by trivial reordering. This function thus accepts an array of costs for a user-selected state realization, and assembles the correct cost matrix for the state realization selected by MTK. To do this, the funciton performs a linearization between inputs and the cost outputs. The linearization is used to determine the matrix entries belonging to states that are not part of the realization chosen by MTK.

Arguments:

  • sys: The system to be linearized (not simplified).
  • inputs: A vector of variables that are to be considered controlled inputs for the LQR controller.
  • costs: A vector of pairs.

ControlSystemsMTK.fundamental_response — Method
fundamental_response(ml::MultirateLinearization, u, y, w)

The complex amplitude of the component with the angular frequency of the input in the steady-state response of the output y to the input u = exp(im*w*t), for each element of the frequency vector w.

For a time-invariant system this is the frequency response. For a sampled-data system it is one entry of the harmonic response: it is not a transfer function, and neither closed-loop stability nor stability margins can be concluded from it. The result refers to the input held on its grid and the output observed on its grid; with a fine grid for signals of the continuous-time partition (oversample), the result for a sensitivity function approaches the fundamental sensitivity function of Goodwin and Salgado (1994).

See also harmonic_response and performance_frequency_gain.

ControlSystemsMTK.harmonic_response — Method
harmonic_response(ml::MultirateLinearization, u, y, w, k)

The complex amplitude of the component with angular frequency w + 2πk/Tc in the steady-state response of the output y to the input u = exp(im*w*t), for each element of the frequency vector w. u and y are names or indices of signals of ml. The signals are required to have uniformly spaced instants.

k = 0 gives the fundamental_response. The components with k ≠ 0 are caused by sampling and holding and are absent in a time-invariant system. An output with n instants per period distinguishes n components, k = 0, …, n - 1; other values of k coincide with one of these.

ControlSystemsMTK.lifted_ss — Method
lifted_ss(ml::MultirateLinearization)

The time-invariant system that is equivalent to the periodic model ml, obtained by lifting over one period: a discrete-time NamedStateSpace with the common period as sample interval, in which a signal with n instants per period is represented by the n channels s@1, …, s@n in chronological order. The state is the state of ml before the first event of the period, and the state matrix is the monodromy matrix.

The H∞ norm of the lifted system is the induced ℓ2 norm between the sequences of the sampled signals.

ControlSystemsMTK.multipliers — Method
multipliers(ml::MultirateLinearization)

The characteristic multipliers of the periodic model: the eigenvalues of the monodromy matrix. The model is exponentially stable if and only if all multipliers have magnitude smaller than one. Hold variables that are redundant contribute multipliers that are zero.

ControlSystemsMTK.multirate_linearization — Method
multirate_linearization(hl; oversample = 1, t0 = 0.0, continuous_rate = :fastest, inputs = nothing, outputs = nothing, tol = 1e-9)
multirate_linearization(sys, inputs, outputs; oversample, t0, continuous_rate, tol, kwargs...)

Create a MultirateLinearization: a linear periodic model of a hybrid system whose clocked partitions are on periodic clocks with commensurate periods and arbitrary phases. hl is a ModelingToolkit.HybridLinearization, the result of ModelingToolkit.linearize_hybrid, or of get_sensitivity, get_comp_sensitivity and get_looptransfer with hybrid = true. The second method calls linearize_hybrid with kwargs.

The operations at an event are, in this order:

  1. Inputs of the continuous-time partition that are specified by the user take their new values, if the event is an instant of their grid.
  2. The signals of the continuous-time partition that are sampled are evaluated, with the values that the clocked partitions held before the event. A sampled signal with direct feedthrough from a held signal thus contains the previously held value, and a sampled signal with direct feedthrough from a user input contains its new value.
  3. The clocked partitions that tick compute their outputs from their state before the event, and then update their state. A clocked signal that is read through Sample(Hold(x)) has the value that was held before the event: if x is computed at the same instant, the reader obtains its previous value. A clocked signal that is read through another operator, such as Latest of SynchToolkit, has the value computed at the same instant. Outputs that depend directly on each other in a cycle through such operators are rejected.
  4. The held values are updated, and outputs of the continuous-time partition that are specified by the user are observed, if the event is an instant of their grid.
  5. The continuous-time partition is integrated exactly to the next event with constant inputs.

Keyword arguments

  • continuous_rate: Inputs and outputs of the continuous-time partition are held and observed on a uniform grid. With :fastest, the interval of the grid is the smallest clock period divided by oversample; with :period, it is the common period.
  • oversample: An integer that refines the grid of the signals of the continuous-time partition, which makes the behavior between the ticks of the clocks visible. The ticks of the clocks are not changed.
  • t0: The instant at which the period starts. The characteristic multipliers do not depend on t0, the input-output behavior does.
  • inputs, outputs: The variables that were used as inputs and outputs of the linearization. They are required to recover the order of the signals if these belong to several clock partitions.
  • tol: Relative tolerance for the recognition of commensurate periods and of coinciding instants: instants closer than tol*Tc are treated as one event.

The linearization is required to be performed in a stationary operating point of the whole model. This is not verified.

ControlSystemsMTK.multirate_margins — Method
multirate_margins(S::MultirateLinearization; σ = 0, N = 400)
multirate_margins(sys, ap; σ = 0, N = 400, kwargs...)

Stability margins of a periodic loop at a break point. S is the sensitivity function at the break point, with one signal as input and output, for example created from get_sensitivity(sys, ap; hybrid = true). The second method computes the sensitivity function at the analysis point ap of sys; kwargs are passed to multirate_linearization and to the linearization.

The signal at the break point has n instants per period, and a perturbation of it is classified by its action on the n lifted channels. The result is a named tuple with one margin per class of perturbations:

  • gain_interval: A numerical estimate of the interval of constant real positive gains at the break point, containing the gain one, for which the loop is stable and well posed. Gains at which the loop is not well posed are computed from the feedthrough matrix; the loss of stability is located by a search with relative step 0.002 from the gain one, followed by bisection, which can miss an interval of unstable gains that is narrower than the step. A limit of 0 or Inf states that no boundary was found within the search range (1e-4, 1e4).
  • disk_margin_lti_lower_bound: A RobustAndOptimalControl.Diskmargin for time-invariant dynamic perturbations at the rate of the signal. Such a perturbation takes values at the n frequencies that are aliases of each other, which are independent for a complex perturbation without further restrictions, and the margin is computed from an upper bound of the structured singular value with n independent complex scalars. It is a lower bound of the margin for this class on the grid of N frequencies; a peak between the frequencies of the grid is not detected. A perturbation with real coefficients, a fixed order, or the form of a delay belongs to a smaller class.
  • disk_margin_dynamic: A Diskmargin for arbitrary dynamic perturbations of the lifted signal, with the radius 1/‖S + (σ - 1)/2‖∞, where S is the lifted sensitivity function. This class includes periodically time-varying perturbations, and also perturbations that are not causal within the period. It is conservative for time-invariant perturbations.

For n = 1 the loop at the break point is time invariant and both disk margins are computed from the H∞ norm. Their radius agrees with RobustAndOptimalControl.diskmargin(L, σ) for the loop-transfer function L = 1/S - 1, which is the negative of the loop-transfer function that ModelingToolkit.get_looptransfer returns. S is required to be stable.

All margins refer to the signal as it is represented in S. A signal of the continuous-time partition is represented by its values on the grid selected by continuous_rate and oversample: the perturbation acts between the observation of the signal on the grid and a hold on the grid. The margins then apply to the continuous-time signal itself only if moving the perturbation to the grid changes no value that is sampled from the signal, including the values that are read at an instant that coincides with an instant of the grid.

σ is the skew of the disk.

performance_frequency_gain(ml::MultirateLinearization, u, y, w)

ControlSystemsMTK.robust_frequency_gain — Method
robust_frequency_gain(ml::MultirateLinearization, u, y, w)

The largest singular value of the frequency response of the lifted system between the signals u and y, for each element of the frequency vector w: the largest gain, in terms of the energy of the sequences of sampled values, over all inputs that are composed of the frequencies w + 2πk/Tc. The result is periodic in w with period 2π/Tc, and for a stable model its supremum is the H∞ norm of the lifted system between the two signals, that is, the induced ℓ2 norm between the sequences of their sampled values. For signals with n_u and n_y instants per period, performance_frequency_gain ≤ sqrt(n_u/n_y)*robust_frequency_gain.

ControlSystemsMTK.single_rate_ss — Method
single_rate_ss(hl; Ts, method = :tustin, w_prewarp = 0)
single_rate_ss(sys, inputs, outputs; Ts, method = :tustin, w_prewarp = 0, kwargs...)

A time-invariant approximation of a hybrid model with several clocks, obtained by converting all partitions of the ModelingToolkit.HybridLinearization hl to one common rate and closing the connections between them. Ts = 0 gives a continuous-time system, in which each clocked partition is converted with d2c. With Ts > 0, the continuous-time partition is discretized with c2d, a clocked partition with the sample interval Ts is used as it is, and each other clocked partition is converted to continuous time and discretized again. method and w_prewarp are passed to c2d and d2c. The phases of the clocks are not represented.

The result is an approximation: a model with several clocks is periodically time varying, and aliasing between the rates is not represented. In the continuous-time result the holds are not represented either. No stability or robustness property of the model follows from the result. multirate_linearization provides an exact representation for commensurate periods; single_rate_ss is also applicable when the periods are not commensurate.

RobustAndOptimalControl.named_ss — Method
RobustAndOptimalControl.named_ss(sys::ModelingToolkit.AbstractSystem, inputs, outputs; descriptor=true, simple_infeigs=true, balance=false, kwargs...)

Convert an System to a NamedStateSpace using linearization. inputs, outputs are vectors of variables determining the inputs and outputs respectively. See docstring of ModelingToolkit.linearize for more info on kwargs.

If descriptor = true (default), this method automatically converts systems that MTK has failed to produce a proper form for into a proper linear statespace system using the method described here: https://juliacontrol.github.io/ControlSystemsMTK.jl/dev/#Internals:-Transformation-of-non-proper-models-to-proper-statespace-form If descriptor = false, the system is instead converted to a statespace realization using sys[:,uinds] + sys[:,duinds]*tf('s'), which tends to result in a larger realization on which the user may want to call minreal(sys, tol) with a carefully selected tolerance.

Hybrid models

A model that contains clocked (discrete-time) partitions connected to the continuous-time equations is linearized as a hybrid model if hybrid = true. This is the default if additional_passes contains a discrete compilation pass, such as SynchToolkit.compile_lustre, and also if ModelingToolkit rejects the model as a hybrid model because no such pass was supplied. Each clock partition is then linearized separately with ModelingToolkit.linearize_hybrid and the partitions are assembled into a single discrete-time system: the continuous-time partition is discretized with zero-order hold at the sample interval of the clock and the connections across the clock boundaries are closed. Inputs that belong to the continuous-time partition are consequently assumed to be piecewise constant between the sample instants, and outputs of the continuous-time partition are obtained at the sample instants only. All clocked partitions are required to be on the same periodic clock, and the continuous-time partition must not have direct feedthrough from a held signal to a sampled signal. The HybridLinearization returned by linearize_hybrid is stored in extra[:hybrid_linearization] of the result, and kwargs are forwarded to linearize_hybrid. With hybrid = false, the model is passed to ModelingToolkit.linearize, the result of which does not include the clocked partitions.

See also ModelingToolkit.linearize which is the lower-level function called internally. The functions get_named_sensitivity, get_named_comp_sensitivity, get_named_looptransfer similarily provide convenient ways to compute sensitivity functions while retaining signal names in the same way as named_ss. The corresponding lower-level functions get_sensitivity, get_comp_sensitivity and get_looptransfer are available in ModelingToolkitStandardLibrary.Blocks and are documented in MTKstdlib: Linear analysis.

ModelingToolkit.linearize — Function
(; A, B, C, D), simplified_sys, extras = linearize(sys, inputs, outputs;    t=0.0, op = Dict(), allow_input_derivatives = false, zero_dummy_der=false, kwargs...)
(; A, B, C, D), extras                 = linearize(simplified_sys, lin_fun; t=0.0, op = Dict(), allow_input_derivatives = false, zero_dummy_der=false)

Linearize sys between inputs and outputs, both vectors of variables. Return a NamedTuple with the matrices of a linear statespace representation on the form

\[\begin{aligned} ẋ &= Ax + Bu\\ y &= Cx + Du \end{aligned}\]

The first signature automatically calls linearization_function internally, while the second signature expects the outputs of linearization_function as input.

op denotes the operating point around which to linearize. If none is provided, the default values of sys are used.

If allow_input_derivatives = false, an error will be thrown if input derivatives ($u̇$) appear as inputs in the linearized equations. If input derivatives are allowed, the returned B matrix will be of double width, corresponding to the input [u; u̇].

zero_dummy_der can be set to automatically set the operating point to zero for all dummy derivatives.

The return value extras is a NamedTuple (; x, p, t) containing the result of the initialization problem that was solved to determine the operating point.

See also linearization_function which provides a lower-level interface, linearize_symbolic and ModelingToolkit.reorder_unknowns.

See extended help for an example.

The implementation and notation follows that of "Linear Analysis Approach for Modelica Models", Allain et al. 2009

Extended help

This example builds the following feedback interconnection and linearizes it from the input of F to the output of P.


  r ┌─────┐       ┌─────┐     ┌─────┐
───►│     ├──────►│     │  u  │     │
    │  F  │       │  C  ├────►│  P  │ y
    └─────┘     ┌►│     │     │     ├─┬─►

using ModelingToolkit
using ModelingToolkit: t_nounits as t, D_nounits as D
function plant(; name)
    @variables x(t) = 1
    @variables u(t)=0 y(t)=0
    eqs = [D(x) ~ -x + u
           y ~ x]
    System(eqs, t; name = name)
end

function ref_filt(; name)
    @variables x(t)=0 y(t)=0
    @variables u(t)=0 [input = true]
    eqs = [D(x) ~ -2 * x + u
           y ~ x]
    System(eqs, t, name = name)
end

function controller(kp; name)
    @variables y(t)=0 r(t)=0 u(t)=0
    @parameters kp = kp
    eqs = [
        u ~ kp * (r - y),
    ]
    System(eqs, t; name = name)
end

@named f = ref_filt()
@named c = controller(1)
@named p = plant()

connections = [f.y ~ c.r # filtered reference to controller reference
               c.u ~ p.u # controller output to plant input
               p.y ~ c.y]

@named cl = System(connections, t, systems = [f, c, p])

lsys0, ssys = linearize(cl, [f.u], [p.x])
desired_order = [f.x, p.x]
lsys = ModelingToolkit.reorder_unknowns(lsys0, unknowns(ssys), desired_order)

@assert lsys.A == [-2 0; 1 -2]
@assert lsys.B == [1; 0;;]
@assert lsys.C == [0 1]
@assert lsys.D[] == 0

## Symbolic linearization
lsys_sym, _ = ModelingToolkit.linearize_symbolic(cl, [f.u], [p.x])

@assert substitute(lsys_sym.A, ModelingToolkit.defaults(cl)) == lsys.A

ModelingToolkit.linearization_function — Function
lin_fun, simplified_sys = linearization_function(sys::AbstractSystem, inputs, outputs; simplify = false, initialize = true, initialization_solver_alg = nothing, kwargs...)

Return a function that linearizes the system sys. The function linearize provides a higher-level and easier to use interface.

lin_fun is a function (variables, p, t) -> (; f_x, f_z, g_x, g_z, f_u, g_u, h_x, h_z, h_u), i.e., it returns a NamedTuple with the Jacobians of f,g,h for the nonlinear sys (technically for simplified_sys) on the form

\[\begin{aligned} ẋ &= f(x, z, u) \\ 0 &= g(x, z, u) \\ y &= h(x, z, u) \end{aligned}\]

where x are differential unknown variables, z algebraic variables, u inputs and y outputs. To obtain a linear statespace representation, see linearize. The input argument variables is a vector defining the operating point, corresponding to unknowns(simplified_sys) and p is a vector corresponding to the parameters of simplified_sys. Note: all variables in inputs have been converted to parameters in simplified_sys.

The simplified_sys has undergone ModelingToolkitBase.mtkcompile and had any occurring input or output variables replaced with the variables provided in arguments inputs and outputs. The unknowns of this system also indicate the order of the unknowns that holds for the linearized matrices.

Arguments:

  • sys: A System of ODEs. This function will automatically apply simplification passes on sys and return the resulting simplified_sys.
  • inputs: A vector of variables that indicate the inputs of the linearized input-output model.
  • outputs: A vector of variables that indicate the outputs of the linearized input-output model.
  • simplify: Apply simplification in tearing.
  • initialize: If true, a check is performed to ensure that the operating point is consistent (satisfies algebraic equations). If the op is not consistent, initialization is performed.
  • initialization_solver_alg: A NonlinearSolve algorithm to use for solving for a feasible set of state and algebraic variables that satisfies the specified operating point.
  • autodiff: An ADType supported by DifferentiationInterface.jl to use for calculating the necessary jacobians. Defaults to using AutoForwardDiff()
  • op: The operating point, a dictionary or a LinearizationOpPoint. A LinearizationOpPoint determines the operating point and t from its solution at its first time point, and implies ignore_system_initial_conditions = true, as in linearize. This allows passing a LinearizationOpPoint to the functions that build on linearization_function, such as get_sensitivity.
  • ignore_system_initial_conditions: Whether to ignore initial_conditions(sys) and only use op.
  • loop_openings: Analysis points whose connections are removed before linearization, also when inputs and outputs are variables. A signal disconnected by a loop opening is held at the value of the signal that drove it unless op provides a value for it.
  • system_modifier: A function applied to the system after the loop openings and before structural simplification.
  • verbose: An MTKVerbosity, a SciMLLogging preset, or a Bool controlling diagnostic output (the empty_operating_point toggle and the initialization toggles). The deprecated boolean keywords warn_empty_op and warn_initialize_determined remain accepted and override the corresponding toggles when explicitly passed.
  • specialize: The SciMLBase.AbstractSpecialization of the ODEProblem built for the system, or nothing for ODEProblem's default. With SciMLBase.FullSpecialize, the system and observed functions are called directly instead of through function wrappers, so the evaluation is fully specialized; eval_expression and eval_module also apply to the system function; and with initialize = false, a call whose u and p have the types of the problem's uses them as given, without remaking the problem.
  • kwargs: Are passed on to find_solvables!

See also linearize which provides a higher-level interface.

ControlSystemsBase.loopshapingPID — Function
C, kp, ki, kd, fig, CF = loopshapingPID(P, ω; Mt = 1.3, ϕt=75, form=:standard, doplot=false, lb=-10, ub=10, Tf = 1/1000ω, F = nothing)

Selects the parameters of a PID-controller such that the Nyquist curve of the loop-transfer function $L = PC$ at the frequency ω is tangent to the circle where the magnitude of $T = PC / (1+PC)$ equals Mt. ϕt denotes the positive angle in degrees between the real axis and the tangent point.

The default values for Mt and ϕt are chosen to give a good design for processes with inertia, and may need tuning for simpler processes.

The gain of the resulting controller is generally increasing with increasing ω and Mt.

Arguments:

  • P: A SISO plant.
  • ω: The specification frequency.
  • Mt: The magnitude of the complementary sensitivity function at the specification frequency, $|T(iω)|$.
  • ϕt: The positive angle in degrees between the real axis and the tangent point.
  • doplot: If true, gang of four and Nyquist plots will be returned in fig.
  • lb: log10 of lower bound for kd.
  • ub: log10 of upper bound for kd.
  • Tf: Time constant for second-order measurement noise filter on the form tf(1, [Tf^2, 2*Tf/sqrt(2), 1]) to make the controller strictly proper. A practical controller typically sets this time constant slower than the default, e.g., Tf = 1/100ω or Tf = 1/10ω
  • F: A pre-designed filter to use instead of the default second-order filter.

The parameters can be returned as one of several common representations chosen by form, the options are

  • :standard - $K_p(1 + 1/(T_i s) + T_ds)$
  • :series - $K_c(1 + 1/(τ_i s))(τ_d s + 1)$
  • :parallel - $K_p + K_i/s + K_d s$

See also loopshapingPI, pidplots, stabregionPID and placePI.

Example:

P  = tf(1, [1,0,0]) # A double integrator
Mt = 1.3  # Maximum magnitude of complementary sensitivity
ω  = 1    # Frequency at which the specification holds
C, kp, ki, kd, fig, CF = loopshapingPID(P, ω; Mt, ϕt = 75, doplot=true)

RobustAndOptimalControl.named_ss — Function
RobustAndOptimalControl.named_ss(sys::ModelingToolkit.AbstractSystem, inputs, outputs; descriptor=true, simple_infeigs=true, balance=false, kwargs...)

Convert an System to a NamedStateSpace using linearization. inputs, outputs are vectors of variables determining the inputs and outputs respectively. See docstring of ModelingToolkit.linearize for more info on kwargs.

If descriptor = true (default), this method automatically converts systems that MTK has failed to produce a proper form for into a proper linear statespace system using the method described here: https://juliacontrol.github.io/ControlSystemsMTK.jl/dev/#Internals:-Transformation-of-non-proper-models-to-proper-statespace-form If descriptor = false, the system is instead converted to a statespace realization using sys[:,uinds] + sys[:,duinds]*tf('s'), which tends to result in a larger realization on which the user may want to call minreal(sys, tol) with a carefully selected tolerance.

Hybrid models

A model that contains clocked (discrete-time) partitions connected to the continuous-time equations is linearized as a hybrid model if hybrid = true. This is the default if additional_passes contains a discrete compilation pass, such as SynchToolkit.compile_lustre, and also if ModelingToolkit rejects the model as a hybrid model because no such pass was supplied. Each clock partition is then linearized separately with ModelingToolkit.linearize_hybrid and the partitions are assembled into a single discrete-time system: the continuous-time partition is discretized with zero-order hold at the sample interval of the clock and the connections across the clock boundaries are closed. Inputs that belong to the continuous-time partition are consequently assumed to be piecewise constant between the sample instants, and outputs of the continuous-time partition are obtained at the sample instants only. All clocked partitions are required to be on the same periodic clock, and the continuous-time partition must not have direct feedthrough from a held signal to a sampled signal. The HybridLinearization returned by linearize_hybrid is stored in extra[:hybrid_linearization] of the result, and kwargs are forwarded to linearize_hybrid. With hybrid = false, the model is passed to ModelingToolkit.linearize, the result of which does not include the clocked partitions.

See also ModelingToolkit.linearize which is the lower-level function called internally. The functions get_named_sensitivity, get_named_comp_sensitivity, get_named_looptransfer similarily provide convenient ways to compute sensitivity functions while retaining signal names in the same way as named_ss. The corresponding lower-level functions get_sensitivity, get_comp_sensitivity and get_looptransfer are available in ModelingToolkitStandardLibrary.Blocks and are documented in MTKstdlib: Linear analysis.

ModelingToolkit.linearize_symbolic — Function
matrices, simplified_sys = linearize_symbolic(sys::AbstractSystem, inputs, outputs;
    simplify = false,
    allow_input_derivatives = false,
    eval_expression = false,
    eval_module = @__MODULE__,
    split = true,
    kwargs...)

Symbolically linearize sys between inputs and outputs.

Unlike linearize, this uses Symbolics.jacobian and returns symbolic matrices instead of numerical matrices evaluated at an operating point.

Arguments

  • sys: the system to linearize. This function calls ModelingToolkitBase.mtkcompile internally.
  • inputs: input variables used as the columns of the B and D matrices.
  • outputs: output variables used as the rows of the C and D matrices.

Keyword Arguments

  • simplify: whether to run additional symbolic simplification during compilation.
  • allow_input_derivatives: whether differentiated inputs may appear in the linearized equations. If true, B and D include extra columns for those derivatives.
  • eval_expression: whether generated expressions are evaluated directly instead of using runtime-generated functions.
  • eval_module: the module used when eval_expression = true.
  • split: whether generated functions use a tuple of parameters or splatted parameters.
  • kwargs...: additional keyword arguments forwarded to ModelingToolkitBase.mtkcompile.

Returns

A pair (matrices, simplified_sys). matrices is a NamedTuple containing A, B, C, and D, plus the symbolic Jacobian blocks f_x, f_z, g_x, g_z, f_u, g_u, h_x, h_z, and h_u of

\[\begin{aligned} ẋ &= f(x, z, u) \\ 0 &= g(x, z, u) \\ y &= h(x, z, u) \end{aligned}\]

Here x are differential unknowns, z are algebraic unknowns, u are inputs, and y are outputs.

Examples

ModelingToolkitStandardLibrary.Blocks.StateSpace — Function
StateSpace(A, B, C, D = 0; x = zeros(size(A,1)), u0 = zeros(size(B,2)), y0 = zeros(size(C,1)), name)

A linear, time-invariant state-space system on the form.

\[\begin{aligned} ẋ &= Ax + Bu \\ y &= Cx + Du \end{aligned}\]

Transfer functions can also be simulated by converting them to a StateSpace form.

y0 and u0 can be used to set an operating point, providing them changes the dynamics from an LTI system to the affine system

\[\begin{aligned} ẋ &= Ax + B(u - u0) \\ y &= Cx + D(u - u0) + y0 \end{aligned}\]

For a nonlinear system

\[\begin{aligned} ẋ &= f(x, u) \\ y &= h(x, u) \end{aligned}\]

linearized around the operating point x₀, u₀, we have y0, u0 = h(x₀, u₀), u₀.

SymbolicControlSystems.ccode — Function
ccode(G; simplify = identity, cse = true, static = true, double = true)

Return a string with C-code for filtering a signal u through G.

If G is a transfer function, the system must be SISO, for MIMO systems, use a StateSpace model instead.

With a transfer function as input, the code will return a double corresponding to the single output. With a StateSpace model as input, the code will produce a function that takes a double pointer double *y as the first input argument. Make sure that y points to an array of length G.ny before calling the function.

The state is internally handled by C static variables, so the generated code is thus stateful.

Arguments:

  • simplify: A function for symbolic simplification. You may try Sympy.simplify, but for large systems, this will take a long time to compute.

  • static: If true, the generated code will use static variables to store the state of the system. If false, the function will take pointers to the state variables as input arguments.
  • double: If true, the generated code will use double as the numeric type. If false, it will use float.
